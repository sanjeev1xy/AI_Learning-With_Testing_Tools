# Jira QA Crew — AI-Powered QA Artifact Generator

Enter one or more Jira ticket IDs and get a complete QA package: requirements
analysis, a 12-section test plan, traceable test cases, a requirements→tests
traceability matrix, and Playwright TypeScript automation — generated by a
sequential **CrewAI** four-agent pipeline and rendered by deterministic Python.

The processing engine is real CrewAI (`Agent` / `Task` / `Crew`). Agents are
never simulated with hard-coded responses. Every artifact is built from a
validated Pydantic object, not from raw LLM markdown.

---

## Pipeline

```
Jira ID(s)
  → Jira Analyst Agent      (fetch via MCP → REST fallback; extract requirements)
  → Test Plan Writer Agent  (12-section plan, every scenario tied to REQ-*/AC-*)
  → Test Case Writer Agent  (detailed, traceable test cases)
  → Playwright Coder Agent  (@playwright/test specs for automatable cases)
  → Deterministic validation + traceability + coverage
  → Artifact generation (md / json / csv / .spec.ts / manifest / ZIP)
  → Streamlit results UI
```

Each ticket runs in a **fresh crew context** so information never leaks between
tickets. Processing continues if one ticket fails; a run succeeds if at least one
ticket completes.

## Agents

| # | Agent | Output model | Notes |
|---|-------|--------------|-------|
| 1 | Jira Analyst | `RequirementAnalysis` | Only agent with Jira access. Marks EXPLICIT / INFERRED / MISSING / ASSUMPTION. Never invents requirements. |
| 2 | Test Plan Writer | `TestPlan` | Exactly 12 numbered sections; scenarios reference REQ-*/AC-*. |
| 3 | Test Case Writer | `TestCaseSuite` | Every explicit AC gets ≥1 positive test; automation candidate Yes/No/Partial. |
| 4 | Playwright Coder | `PlaywrightBundle` | Automates only Yes/Partial cases. No `waitForTimeout`, no hard-coded secrets/URLs. Emits `NEEDS_CONFIGURATION` scaffold when UI details are missing. |

## Configuration

All settings come from environment variables / `.env` / `.streamlit/secrets.toml`.
See `.env.example` for the full list. Key ones:

| Var | Meaning |
|-----|---------|
| `LLM_MODEL` | Any LiteLLM/CrewAI model id. Not hard-coded anywhere. |
| `LLM_API_KEY`, `LLM_BASE_URL` | LLM credentials / OpenAI-compatible endpoint. |
| `JIRA_INTEGRATION_MODE` | `auto` (MCP→REST), `mcp`, or `rest`. |
| `JIRA_URL`, `JIRA_EMAIL`, `JIRA_API_TOKEN` | Jira Cloud REST (Basic auth). |
| `JIRA_BEARER_TOKEN` + `JIRA_AUTH_MODE=bearer` | Bearer auth alternative. |
| `JIRA_ACCEPTANCE_CRITERIA_FIELD` | Custom field id for acceptance criteria. |
| `JIRA_MCP_URL` / `JIRA_MCP_COMMAND` | MCP server (streamable HTTP or stdio). |
| `JIRA_MCP_GET_ISSUE_TOOL` | Override if tool auto-detection fails. |
| `DEMO_MODE` | `true` serves `fixtures/` data **only when no live Jira is configured**. |

### Jira MCP setup

Point `JIRA_MCP_URL` at a running Jira MCP server (streamable HTTP), or set
`JIRA_MCP_COMMAND`/`JIRA_MCP_ARGS_JSON` for a stdio server (e.g.
`JIRA_MCP_COMMAND=uvx`, `JIRA_MCP_ARGS_JSON=["mcp-atlassian"]`). The gateway
auto-detects a get-issue tool from a candidate list; override with
`JIRA_MCP_GET_ISSUE_TOOL`. Only read-only tools are ever invoked — write /
transition / delete / admin tools are never called.

### Jira REST fallback

Uses `GET /rest/api/3/issue/{key}`, parses ADF, retries transient failures with
backoff, and raises typed errors for 401/403/404/429. In `auto` mode it is used
automatically when MCP is disabled, unavailable, times out, or returns
unusable data.

## Run the Streamlit app

```bash
streamlit run app.py
```

Then enter e.g. `VWO-48` or `VWO-48, VWO-49` and click **Analyze & Generate QA
Pack**. IDs may be separated by commas, spaces, new lines or semicolons; they are
upper-cased, de-duplicated and validated against `JIRA_KEY_PATTERN`.

## Demo mode

Set `DEMO_MODE=true` with no Jira credentials configured. The UI shows a
**DEMO MODE** banner, tickets are served from `fixtures/*.json` tagged
`source=FIXTURE`, and the full four-agent pipeline still runs against the real
LLM. Demo data is **never** an automatic fallback for a failed live integration —
a live fetch failure raises a typed error instead.

When a ticket key has no matching fixture, `DEMO_ALLOW_SYNTHETIC=true` (default)
serves a **clearly-labelled SYNTHETIC placeholder ticket** so the pipeline still
runs end-to-end; the UI shows a "SYNTHETIC DEMO TICKET" warning and the artifacts
are marked illustrative. Set `DEMO_ALLOW_SYNTHETIC=false` to require a real
fixture instead.

## Run persistence

Every completed run is snapshotted to `outputs/<run_id>/run_result.json`. The
Streamlit app restores the most recent run on load and offers a **Previous runs**
picker, so results survive page reloads, websocket drops, and app restarts even
though a pipeline run can take minutes. Runs produced before this snapshot
existed are reconstructed from their artifacts on first launch.

### Playwright validation

Generated projects include `package.json`, `tsconfig.json` and
`playwright.config.ts`. Where Node is available:

```bash
cd outputs/<run_id>/<TICKET>/playwright
npm install
npx playwright test --list
```

If Node is unavailable, the generated TypeScript structure is still validated
(imports, no `waitForTimeout`, no hard-coded secrets) by `services/validation.py`.

## Security notes

- Secrets only from env / `st.secrets`; redacted in logs, errors and the UI.
- Read-only Jira access; no writes, transitions, or admin tools.
- Jira content is treated as untrusted data — embedded instructions are ignored.
- Ticket input is size- and count-limited; all artifact path segments are
  sanitised (no directory traversal).
- No `eval`/`exec`, no shell execution from Jira content, no Playwright execution
  from the Streamlit server.

## Troubleshooting

- **Jira `503 ... SUSPENDED_INACTIVITY` / "subscription has been deactivated due
  to inactivity"** — the Atlassian Cloud site auto-suspended. Sign in to the site
  URL in a browser to reactivate it (takes a few minutes), then retry. This is an
  Atlassian site state, not an app bug; the app surfaces the message verbatim.
  Meanwhile `DEMO_MODE=true` keeps the UI usable on fixtures.
- **`DEMO_MODE`** is an explicit switch — `true` always uses fixtures, `false`
  always uses live Jira (a live failure errors, never silently falls back).
- **Groq `429 ... tokens per minute (TPM): Limit 8000`** — the free tier caps a
  *single request* (prompt + completion + reasoning) at 8000 tokens/minute. Keep
  `PIPELINE_MAX_RPM` low (default `3`), `LLM_MAX_TOKENS` ≈ 5000, and
  `LLM_REASONING_EFFORT=low`. The pipeline also backs off and retries automatically.
- **Groq model id** — Groq's own id is `openai/gpt-oss-120b`; CrewAI strips one
  `openai/` prefix for custom endpoints, so `build_llm` sends `openai/openai/...`.
  `gpt-oss-120b` is stronger for the strict-JSON stages; `gpt-oss-20b` is lighter
  on the rate limit. Set `LLM_MODEL` to whichever your quota allows.
- **`StreamlitDuplicateElementId`** — fixed; every per-ticket widget carries a
  ticket-scoped `key`.

## Limitations

- Live Jira MCP / REST require real credentials; without them the app runs in
  DEMO MODE and live integration is unverified.
- The LLM must be configured (`LLM_MODEL` + `LLM_API_KEY`) — CrewAI cannot run
  otherwise.
- `npx playwright test --list` requires Node.js + `npm install` in the generated
  project.
