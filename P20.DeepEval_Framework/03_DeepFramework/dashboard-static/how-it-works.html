How the DeepEval Framework works

Subsystem C of P20.DeepEval_Framework. It scores two live LLM apps — a support chatbot and a RAG pipeline — with a separate judge LLM, and reports the result as a pytest suite and a web dashboard.

25 metrics2 targets1 judge 263 pytest cases5 categories

The pipeline

One evaluation of one metric is a single pass through this pipeline. The judge is a different model from the app being tested — both hosted on Groq — because a judge scoring its own model family inflates the score.

The two targets

ShopSphere chatbot (Subsystem A)8201ChatbotTargetreply

Most metrics run against both. The dashboard's Target selector and the @pytest.mark.rag / @pytest.mark.chatbot markers pick which.

Score direction is not uniform in DeepEval 4.x. For the 4.x safety metrics and the G-Eval rubrics, 1.0 is good and the threshold is the minimum passing score. The framework normalises this so a green card always means "the app behaved well".

Why the judge is a different model

The chatbot and RAG bot answer with qwen/qwen3.8-27b. The judge is openai/gpt-oss-120b. Both are on Groq's OpenAI-compatible endpoint, wrapped as a DeepEval LocalModel. A judge grading its own family systematically over-rates those answers, so the subject and the judge are deliberately kept in different families.

Running it

The chatbot (8201) and RAG Explorer (8202) must be up first.

# dashboard — one card per metric, Run on demand
uvicorn dashboard.app:app --port 8203        # http://localhost:8203

# headless — same specs, no pytest
python -m dashboard.runner --target rag --limit 2
python -m dashboard.runner --keys correctness role_violation

# pytest
pytest                    # all 263 cases
pytest -m "rag and not slow"
pytest tests/rag/test_00_smoke.py            # no-LLM wiring check

Groq's free tier rate-limits hard, so the runner spaces judge calls (EVAL_CASE_DELAY) and backs off once on a 429 (EVAL_RATE_BACKOFF).
