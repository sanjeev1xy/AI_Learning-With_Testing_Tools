How I Built an Advanced RAG Pipeline

A hybrid-retrieval, re-ranked, grounded-generation system over 5,000 JIRA-format QA test cases — dense + sparse embeddings, Qdrant, cross-encoder re-ranking, and query rewriting, wired together end to end.

1Why "advanced" over a basic RAG?

A basic RAG does one embedding model, one vector search, one LLM call. That's fine for a handful of documents. At 5,000 rows with overlapping vocabulary (lots of test cases share words like "verify", "booking", "user"), pure semantic (dense) search alone starts missing exact-keyword matches — and pure keyword search misses paraphrases. This pipeline layers in the techniques that address that, one deliberate stage at a time.

Most test-case rows are short enough that 1 row = 1 chunk. Longer rows (verbose steps) get split at 1,000 characters with a 150-character overlap, so a sentence that straddles a chunk boundary is never fully lost to one side.

3Hybrid retrieval — one model, two signals

bge-m3 produces both a dense vector (1024-dim, semantic meaning) and a sparse vector (lexical weights per token, like a smarter TF-IDF) from a single forward pass. Both get stored as named vectors on the same Qdrant point.

Dense search catches paraphrases — "sign in fails after 5 tries" retrieves a chunk about "account lockout on repeated failed logins" even with no shared words.
Sparse search catches exact terms — a query for "VWO-1234" or "XXE" retrieves chunks containing that literal token, which dense embeddings alone can blur into a diffuse cloud of "similar-ish" meaning.

4Reciprocal Rank Fusion

Dense and sparse searches return two separately-ranked lists. RRF combines them without needing the raw scores to be on the same scale — it only looks at rank position:

score(doc) = Σ 1 / (k + ranklist(doc))

Chunk A shows up near the top of both lists, so it wins the fused ranking even though it was never literally #1 in either one — that's the point of fusing two independent signals.

5Cross-encoder re-ranking

Dense/sparse search both score a query against a document independently — fast, but approximate. bge-reranker-v2-m3 is a cross-encoder: it reads the query and each candidate chunk together in one pass and outputs a direct relevance score. Much more accurate, much slower — which is exactly why it only runs on the top ~20 RRF candidates, not the full 5,000-row collection.

RRF gives ~20 candidates Reranker scores all 20 pairs Top 4 go to the LLM

6Query rewriting

Before retrieval, the LLM generates two alternate phrasings of the user's question. All three variants get embedded and searched; results are merged by best score per document. This catches cases where the user's exact wording doesn't match how a test case is phrased in the corpus, without requiring the user to rephrase manually.

7Grounded generation — two modes

Answer mode — the default. The LLM answers strictly from the retrieved chunks and cites them inline as [Chunk N]. If the corpus doesn't cover the question, it says so instead of inventing an answer.
Generate mode — auto-detected from phrases like "create a new test case for...". The LLM drafts a new, structured test case (Title / Preconditions / Steps / Expected / Priority / Tags), using the retrieved similar cases as style templates so the output matches the corpus's voice.

8Stack & tunables

Backend: Flask + Server-Sent Events for the live ingest progress stream.
Embeddings: BAAI/bge-m3 (dense + sparse, one model).
Vector DB: Qdrant, embedded/local mode — no Docker required.
Re-ranker: BAAI/bge-reranker-v2-m3 cross-encoder.
LLM: Groq (openai/gpt-oss-120b) for rewriting and generation.
